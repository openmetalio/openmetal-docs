# CEN-1229 — Public API documentation for firewall endpoints

Linear: https://linear.app/openmetal/issue/CEN-1229/public-api-documentation-for-firewall-endpoints

Master copy of the approved plan is the Linear document "Plan: CEN-1229 Public API
documentation for firewall endpoints". This file is the trimmed, `openmetal-docs`-only
slice of it. This ticket also touches `central-api` (central-auth API whitelist, tracked
separately) and calls for a `toolkit` `components.yaml` addition that is out of scope for
implementation — see Deviations below.

## Components in scope

- `openmetal-docs` (this repo)

## Goal

Document `GET`/`PUT /v1/deployment/cloud/{cloudId}/firewall` in the public OpenAPI spec so
customers can drive firewall management via the API, describing the post-CEN-1476 contract
in which `additional_rules` is omitted entirely from both GET and PUT — per the ticket
owner's 2026-09-01 confirmation.

## Changes in this repo

1. **New** `api/paths/firewall.yaml`, keyed by `/v1/deployment/cloud/{cloudId}/firewall`,
   following the `$ref`-to-file convention already used by `paths/vlans.yaml` and
   `paths/clouds-hardware.yaml`. `{cloudId}` (camelCase) matches this repo's existing
   convention for the same path prefix (see `openapi.yaml`'s node-power endpoint), even
   though the internal central-api route param is `cloud_id`.
   - `get`: `customer_whitelist`, `vlans`, `external_vlan_label` (read-only), `status`
     (`{ status, message }`). No `additional_rules` anywhere.
   - `put`: request body is `customer_whitelist` only — no `additional_rules` property.
     `200` response is `{ jobId, status: "pending" }`, documented explicitly as a queued
     acknowledgement, not confirmation the rules are live. `400`/`401`/`403`/`409`
     documented.
2. `api/openapi.yaml`: one `$ref` line for `/v1/deployment/cloud/{cloudId}/firewall`,
   alongside the existing `vlans.yaml`/`clouds-hardware.yaml` entries.

## Test plan

Docs-only change — the Redocly build is the test.

1. `npx @redocly/cli build-docs api/openapi.yaml --output build/api/index.html` exits 0
   with the new `$ref` resolved.
2. `api/paths/firewall.yaml` and the new `$ref` line both exist (were absent before).
3. The built output's PUT request schema lists only `customer_whitelist` — no
   `additional_rules` property — and the GET response schema lists only
   `customer_whitelist`, `vlans`, `external_vlan_label`, `status`.
4. `grep -c additional_rules api/paths/firewall.yaml` returns 0.
5. PUT documents 400, 401, 403, 409; GET documents 401, 403.
6. The PUT `200` response description explicitly states the job is queued/pending and
   directs the caller to poll GET.

## Deviations from the plan (recorded here, not implemented)

The master plan's "Changes by repo — toolkit" section calls for adding an
`openmetal-docs` entry to `plugins/omi-dev/components.yaml` so this component can be
scored by `validate.sh`. **Not implemented**: `implement-ticket`'s Hard Boundaries
explicitly forbid modifying `components.yaml` under any circumstance ("Changing the thing
that judges you is out of bounds, always"), with no carve-out for additions. This means
`validate.sh` cannot score the `openmetal-docs` component for this change — see the AI log
for the manual evidence gathered instead (a direct Redocly build run outside the pipeline).

- Marking `additional_rules` `x-internal` (not achievable — `redocly.yaml` has no
